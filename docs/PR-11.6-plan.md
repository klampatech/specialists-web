## 2. What "server-authoritative damage" actually means

### 2.1 Current damage flow (pre-PR-11.6, in `client/src/game/gameSession.ts` lines 374–425)

Both clients run the **same** simulation with the **same** inputs (per
`client/src/net/ggrsRuntime.ts`'s deterministic-lockstep contract).
When local rises to fire:

1. `dualPistolShoot(input, local, remote, scene)` runs on Tab A — raycasts
   from A's chest forward, finds B's capsule, returns `{hit: true,
   damage: 12}`.
2. `applyDamage(remoteController, {source:"fire", amount:12}, nowMs)` runs
   on Tab A. A's view of B's HP drops by 12.
3. `applyDamage(localController, {source:"fire", amount:12}, nowMs)`
   runs **symmetrically** on Tab B (the peer's rising edge of fire). B's
   view of B's own HP drops by 12.
4. Both clients arrive at identical HP values because the inputs were
   identical and the damage math is a deterministic function of inputs.

This works under LAN / low-loss. **It breaks under WAN loss / jitter**
because the rising-edge can land on slightly different frames on each
client (Phase 0's `~70s no-rollback` documented limitation). Tab A's
"damage landed" frame and Tab B's "damage landed" frame can disagree →
HP diverges per-client.

### 2.2 PR 11.6's new flow

```
┌──────────────┐  DamageRequest        ┌──────────────┐  DamageBroadcast  ┌──────────────┐
│  Tab A (host)│ ────{frame,src,tgt,  │              │ ──{frame,src,tgt, │  Tab B (peer)│
│  client-side  │     amount,nonce}─▶ │   Game       │     amount,nonce,  │  client-side │
│  GameSession │                       │   Server     │     authority}──▶ │  GameSession │
│  (local node) │ ◀──{frame,confirmed}─ │ (Tokio +     │                    │  (peer node) │
└──────────────┘                       │  WebTransport│                    └──────────────┘
                                       │   relay)     │
                                       │              │   ...also broadcasts back to A so A's
                                       │              │   tab applies it via the same path.
                                       └──────────────┘
```

Sequence per damage event:

1. Tab A's `GameSession.tick` calls `dualPistolShoot` (or `meleeSwing`)
   — same code as today. It now returns a `DamageEvent` (already a
   partial struct today: `{hit, damage, source, ...}`) plus a NEW
   `eventId: u32` (counter).
2. Tab A sends `DamageRequest {frame, source, targetPlayerId, amount,
   eventId}` to the server. Tab A does **not** apply damage locally.
3. The server validates: player exists, source is `fire|melee`, amount
   is in `[0, MAX_DAMAGE]`, target ≠ source, frame-monotonic.
4. The server assigns the **canonical frame number** (its own
   server-frame clock, not the tab's local frame), tags it with a
   server-issued monotonic `serverSeq`, and broadcasts `DamageBroadcast`
   to all players in the match (both A and B).
5. Both tabs apply the damage on their local controllers on
   receive — driven by `frame`-aligned entry, not by their own tick
   counter. Identical results ⇒ HP stays symmetric.

### 2.3 Why this works without breaking lockstep

- **Damage is no longer a function of either client's input** — it's a
  function of the server's broadcast order, which is the same for both
  tabs. Both tabs apply the same broadcasts in the same order.
- **Movement, bullet-time, visual stay in the lockstep substrate.**
  PR 11.6 doesn't touch `gameSession.tick`'s physics path; it inserts a
  `serverDamageQueue` that overrides `applyDamage(...)` on receive.
- **Wire-format addition only.** Two new packet types
  (`DamageRequest` + `DamageBroadcast`) on a separate channel from the
  `inputs` lockstep channel. Bytes-on-wire budget: `DamageRequest` =
  14 bytes (frame u32 + source u16 + target u16 + source u8 + amount
  u8 + eventId u32); `DamageBroadcast` = 18 bytes (serverFrame u32 +
  serverSeq u32 + source u16 + target u16 + source u8 + amount u8 +
  originEventId u32). Plus a 14-byte `PositionUpdate` and an 8-byte
  `Ping`/`Pong` pair for lag compensation + RTT (§3.5, §3.4.1).

### 2.4 Determinism contract (preserved + extended)

**Pre-PR-11.6 rule (still applies for movement/combat visuals):**
*Every physics-affecting input is a frame-aligned integer. Never read
`Date.now()` inside the tick.*

**PR 11.6 addition (damage-specific):**
*The HP pool's value, on each client, equals the sum of
`DamageBroadcast.amount` values applied, in receive order, with the
starter HP of 100. Both clients receive identical broadcasts in
identical order ⇒ HP converges without any per-tick timestamping
needed.*

Edge case (called out explicitly): if a `DamageBroadcast` arrives
after the local client's respawn cycle resets HP to 100, the damage
applies to the new HP pool — no special-case code, the math just
falls out because `applyDamage` clamps at 0 and re-arms the respawn
timer when HP crosses 0 (same code as pre-PR-11.6).

### 3.2 Why `Cargo.toml` not a workspace

`client/` is a separate package universe (npm, React, TS). `server/`
doesn't share any code with it — they're connected only by the wire
protocol in `protocol/`. A workspace adds ceremony (root
`Cargo.toml`, `[workspace.dependencies]`) for a single-crate server.
Single-crate `Cargo.toml` is the right grain until Phase 1 adds a
matchmaker (which would be the second crate).

### 3.3 WebTransport vs WebSocket for the client → server transport

Two implementation paths for the PR 11.6 rollout:

| Concern | WebTransport | WebSocket |
|---|---|---|
| Transport semantics | UDP-over-HTTP/3 | TCP |
| Head-of-line blocking | None (QUIC streams) | Yes |
| Browser support (Aug 2026) | Chrome, Edge, FF nightly | Universal |
| Rust crate | `wtransport` (0.x, mature) | `tokio-tungstenite` (mature) |
| Spec match to docs/SPEC §"Stack" | Yes | Degraded |
| Initial implementation cost | Higher (cert handling) | Lower |

**Revised recommendation: WebTransport-first, WebSocket auto-fallback.**

This is a flip from the original plan's WebSocket-first recommendation
(see commit message on this PR for the rationale). The research
underwriting the flip is in `docs/PR-11.6-netcode-research.md` §C;
the short version:

1. **WebSocket head-of-line blocking hides bugs during dev.** Under
   3% packet loss, WebSocket can stall 100-300ms while one packet
   retransmits. That's long enough to make PR 11.5's pause-when-too-far-behind
   cap fire *spuriously*, masking real netcode bugs behind apparent
   "lockstep drift" that only happens because of TCP HOL blocking.
   Discovering this in production (with QUIC) means chasing ghosts.
2. **Browser support is no longer a real constraint.** Chrome, Edge,
   Firefox nightly, and Safari all support WebTransport in 2026. The
   "WebSocket fallback for restricted networks" framing in
   `docs/SPEC.md` §"The stack" still applies — corporate firewalls
   blocking QUIC exist — but it's a fallback, not the primary path.
3. **Dev cost is one self-signed cert.** `tools/canary-server.sh`
   generates a self-signed cert on first run; the browser shows the
   standard "proceed anyway" prompt once. After that it's the same
   dev-loop velocity as WebSocket. Net cost: ~30 minutes in 11.6.B,
   not 1-2 sessions.
4. **Removing the WebTransport follow-up PR (originally 11.6.E)**
   collapses the rollout from 5 sub-PRs to 4 (see §5). Total session
   count is unchanged because 11.6.B grows by ~1 session and 11.6.E
   disappears.

**Implementation shape**:

- Primary: `server` listens on UDP/4433 for WebTransport (HTTP/3);
  `client/src/net/serverTransport.ts` uses the browser `WebTransport`
  API.
- Fallback: `server` ALSO listens on TCP/4434 for WebSocket (so the
  single-binary dev experience doesn't break on networks that block
  QUIC). `client/src/net/serverTransport.ts` tries WebTransport first,
  falls back to WebSocket on connection failure, surfaces the active
  transport in the HUD.
- `cargo` deps: `wtransport` + `tokio-tungstenite`. The single-binary
  serves both.

**This is open question #1 (see §6).** The original answer was
"WebSocket-first, WebTransport-as-followup." The revised answer is
"WebTransport-first, WebSocket-fallback."

#### 3.4.1 Position history + lag compensation (added in this revision)

The original §3.4 sketches a server that validates `source≠target,
amount∈[0,100], eventId monotonic, source type valid` — a *relay* of
player-supplied numbers, not a *validator* of hits. **Without a server
world-model, "validate" reduces to "trust the client"** and the
server-authority boundary is performative only.

Industry standard for shippable server-auth FPS netcode (Valve's
Source/Source 2 lag compensation papers, Riot's Valorant architecture
blog, Overwatch's GDC talks) is **lag compensation via a short position
history buffer** on the server. The server keeps the last N ticks of
every player's position; on a `DamageRequest`, it re-validates the hit
at *the position the shooter saw on their screen* — i.e.,
`serverTime - (clientRttMs / 2) - interpolationDelayMs`. This is what
delivers the "favor the shooter" feel: if it looked like a hit on your
screen, it counts, even if the target has moved behind cover by the
time the packet reaches the server.

**Plan change**: add `server/src/position_history.rs` (~50 lines) +
a new `PositionUpdate` wire type (§3.5). Concretely:

```rust
// server/src/position_history.rs (sketch)
pub struct PositionHistory {
    frames: VecDeque<(ServerFrame, Position)>,
    retention: Duration, // ~1 second at 64Hz = 64 entries per player
}
impl PositionHistory {
    pub fn record(&mut self, frame: ServerFrame, pos: Position) { ... }
    /// Returns the recorded position whose frame is the largest <= t.
    pub fn snapshot_at(&self, t: ServerFrame) -> Option<Position> { ... }
}
```

`Room` gains `position_history: HashMap<PlayerId, PositionHistory>`.
`validate_and_relay()` now:

1. Looks up the target's `PositionHistory.snapshot_at(req.frame - lag_budget)`.
2. Runs `dualPistolShoot` raycast math (ported from
   `client/src/game/combat.ts:dualPistolShoot`) at the historical
   target position, using the historical source yaw/pitch from the
   requester's last `PositionUpdate`.
3. If the raycast hits: build the `DamageBroadcast`. If not: drop the
   request silently (no broadcast).

**Cost**: ~30 lines on the server (`PositionHistory` + `validate_and_relay`
extension), ~14 bytes/frame per player on the wire (`PositionUpdate`),
and a ported copy of `dualPistolShoot`'s raycast math to Rust (~40 lines
in `server/src/hitscan.rs`). Tab side: send one `PositionUpdate` per
tick (or throttled to every other tick at 32Hz — bandwidth vs. accuracy
tradeoff, see §3.10).

**Tradeoff**: small unfairness to the target (they can be hit after
visually clearing a corner on their own screen by up to
`rtt/2 + interpDelay`). This is the industry-accepted tradeoff and
exactly what CS2 / Valorant do — "favor the shooter" is universal in
competitive FPS. Without it, the much larger unfairness swings the
other way (visible misses from lag), which is the "shitty netcode"
complaint class PR 11.6 must avoid.

#### 3.4.2 Fire-rate / ammo validation (added in this revision)

A second validation gap in the original plan: even with lag
compensation, the server doesn't check **whether the shooter is
allowed to be firing**. A malicious or buggy client can send
`DamageRequest{amount=255}` 100x/sec, the server clamps `amount` to
100, and the shooter has effectively built a 100dmg-per-frame cannon.
The §2.2 / §3.4 validation bullets don't cover fire rate.

**Plan change**: extend `validate_and_relay()` with a fire-rate /
ammo gate. Track `last_fire_time: HashMap<(PlayerId, WeaponId),
Instant>` and `ammo: HashMap<PlayerId, AmmoState>` on `Room`. On
incoming `DamageRequest`, check `now - last_fire_time[(source, fire)]
>= COMBAT.dualPistol.fireCooldownMs` (which is `120ms` per
`client/src/game/combat.ts:COMBAT.dualPistol.fireCooldownMs`).

**Why now, not Phase 4**: full anti-cheat (movement-rate plausibility,
statistical anomaly detection) is correctly deferred. But fire-rate
validation on the damage relay is a 10-line check that prevents the
*trivial* cheat on day one. Not having it ships an obvious "console
with 10000hp/sec exploit" hole.

#### 3.4.3 RTT measurement (added in this revision)

Without RTT, lag compensation in §3.4.1 has no `clientRttMs` to feed
it; without RTT, debugging "why is my shot landing wrong" requires
external ping tools instead of in-game diagnostics; without RTT, the
eventual interpolation-buffer tuning (§3.10) is a guess.

**Plan change**: add a `Ping`/`Pong` pair to the wire format (§3.5).
Server responds with `Pong { clientTimestamp, serverTimestamp }` on
every `Ping { clientTimestamp }`. Client maintains a sliding-window RTT
average and exposes it via `getStats() -> { rttMs: number }` on the
`GameTransport` interface. ~10 lines server-side, ~15 lines client-side.

### 3.5 Wire protocol (`protocol/damage.proto` — TypeScript + Rust hand-translated, no codegen)

```typescript
// protocol/damage.ts

/** Tab → Server. "I think this damage happened." */
export interface DamageRequest {
  /** Server-side frame the tab believes this aligns with (informational;
   *  server uses its own frame clock for the broadcast tag). */
  frame: number;
  /** What tab ID is making the claim. */
  sourcePlayerId: u16;
  /** What tab ID is being hit. Must differ from source. */
  targetPlayerId: u16;
  /** Source type — only "fire" and "melee" for PR 11.6. */
  source: 0 | 1; // 0 = fire, 1 = melee
  /** Damage amount. Server clamps to [0, MAX_DAMAGE = 100]. */
  amount: u8;
  /** Tab-issued monotonic counter so the server can dedupe retransmits. */
  eventId: u32;
}

/** Server → all tabs in the room. "This damage is canonical." */
export interface DamageBroadcast {
  /** Server-frame number (server clock). */
  serverFrame: number;
  /** Monotonically-increasing server sequence; tabs ignore out-of-order
   *  broadcasts with this seq. */
  serverSeq: number;
  sourcePlayerId: u16;
  targetPlayerId: u16;
  source: 0 | 1;
  amount: u8;
  /** Original DamageRequest's eventId (for tab-side deduplication if it
   *  ever receives its own request echoed back). */
  originEventId: u32;
}

/** Tab → Server. "Here is my current pose." Sent every tick (or throttled,
 *  see §3.10). Powers the lag-compensation position history on the server
 *  (§3.4.1). */
export interface PositionUpdate {
  serverFrame: u32;
  playerId: u16;
  position: [f32, f32, f32]; // x, y, z — meters, world-space
}

/** Tab → Server. "What's my RTT?" Server responds with Pong.
 *  Used by §3.4.3. */
export interface Ping {
  clientTimestamp: u32;
}

/** Server → Tab. Pong echoes back the original clientTimestamp plus the
 *  server's own clock so clients can also measure server-clock skew. */
export interface Pong {
  clientTimestamp: u32;
  serverTimestamp: u32;
}
```

Wire-encoding shape (matches the existing mixed-endian alignment used
by `client/src/net/inputBitmask.ts` — yaw/pitch are **little-endian** on
bytes 2-5 of the input packet; the existing frame header on the wire
in `ggrsRuntime.ts` is big-endian uint32; **damage protocol uses
big-endian consistently** because the frame counters are larger than
the input counters and BE matches the lockstep substrate):

```
DamageRequest on the wire (14 bytes):
  byte 0..3   frame (u32 BE)
  byte 4..5   sourcePlayerId (u16 BE)
  byte 6..7   targetPlayerId (u16 BE)
  byte 8      source (u8 — 0 fire / 1 melee)
  byte 9      amount (u8)
  byte 10..13 eventId (u32 BE)

DamageBroadcast on the wire (18 bytes):
  byte 0..3   serverFrame (u32 BE)
  byte 4..7   serverSeq (u32 BE)
  byte 8..9   sourcePlayerId (u16 BE)
  byte 10..11 targetPlayerId (u16 BE)
  byte 12     source (u8)
  byte 13     amount (u8)
  byte 14..17 originEventId (u32 BE)

PositionUpdate on the wire (14 bytes):
  byte 0..3   serverFrame (u32 BE)
  byte 4..5   playerId (u16 BE)
  byte 6..9   positionX (f32 BE)
  byte 10..13 positionY (f32 BE)
  // NOTE: 14 bytes = u32 + u16 + 2*f32. Z component fits in a follow-up
  // field if/when vertical movement becomes meaningful; for the demo
  // map (flat ground) Z is constant and can be re-derived server-side
  // from the player's recorded height. If Z becomes required, this
  // grows to 18 bytes (add bytes 14..17 for positionZ f32 BE).

Ping on the wire (4 bytes):
  byte 0..3   clientTimestamp (u32 BE)

Pong on the wire (8 bytes):
  byte 0..3   clientTimestamp (u32 BE)
  byte 4..7   serverTimestamp (u32 BE)
```

**Bytes-on-wire size assertions** in `server/tests/damage_wire.rs`
(three per type, matching the existing plan):
- `assert_eq!(encoded.len(), 14)` for `DamageRequest`
- `assert_eq!(encoded.len(), 18)` for `DamageBroadcast`
- `assert_eq!(encoded.len(), 14)` for `PositionUpdate`
- `assert_eq!(encoded.len(), 4)` for `Ping`
- `assert_eq!(encoded.len(), 8)` for `Pong`

If any of these assertions fail in CI, the wire spec has drifted from
the code — which is exactly the class of off-by-one the original draft
of this section had (it claimed 8 / 13 bytes; the actual sizes are
14 / 18).

### 3.6 The `GgnetTransport` interface stays — new `ServerTransport` is a sibling

`client/src/net/ggnet.ts` is currently:

```typescript
export class GgnetTransport {
  constructor(private peer: WebRTCPeer) {}
  send(p: Uint8Array) { this.peer.send("inputs", p) }
  onPacket(f: (p: Uint8Array) => void) { this.peer.on("packet", f) }
}
```

PR 11.6 changes `ggnet.ts` to:

```typescript
/** Multi-channel abstraction: inputs (existing P2P, unchanged),
 *  damageRequests / damageBroadcasts / positionUpdate / ping (NEW,
 *  server-auth round-trip + lag comp + RTT, §3.4-§3.5), state
 *  (existing P2P, unchanged). */
export interface GameTransport {
  // Existing P2P shape — unchanged.
  sendInputs(p: Uint8Array): void;
  onInputs(f: (p: Uint8Array) => void): void;
  // NEW — server-auth damage round-trip + lag comp.
  sendDamageRequest(p: Uint8Array): void;
  onDamageBroadcast(f: (p: Uint8Array) => void): void;
  /** Send current pose to the server for lag-comp history (§3.4.1). */
  sendPositionUpdate(p: Uint8Array): void;
  /** Send a ping to measure RTT (§3.4.3). */
  sendPing(p: Uint8Array): void;
  onPong(f: (p: Uint8Array) => void): void;
  /** Returns a stats snapshot for HUD / diagnostics. */
  getStats(): { rttMs: number };
  /** Fired when the underlying transport errors out — UI uses this to
   *  show "disconnected" in the HUD. */
  onDisconnect(f: () => void): void;
}
```

Two implementations:

1. **`P2PGgnetTransport`** (existing — wraps `WebRTCPeer`, ignores the
   new methods → throw "not implemented in Phase 0"). Used for the
   legacy signal-only demo path during the migration window.
2. **`ServerGgnetTransport`** (NEW — wraps a WebTransport connection
   primarily + WebSocket fallback per §3.3, multiplexes `inputs` and
   `damage*` and `positionUpdate` and `ping`/`pong` onto separate
   binary message types on the same connection using the first byte as
   a discriminator).

The discriminator format on the wire:
```
byte 0 == 0x00 → inputs (forwarded to lockstep unchanged, INPUT_SIZE bytes)
byte 0 == 0x01 → damageRequest (14 bytes, §3.5)
byte 0 == 0x02 → damageBroadcast (18 bytes, §3.5)
byte 0 == 0x03 → positionUpdate (14 bytes, §3.5)
byte 0 == 0x04 → ping (4 bytes, §3.5)
byte 0 == 0x05 → pong (8 bytes, §3.5)
```
Lengths are unchanged from the existing INPUT_SIZE/PACKET_SIZE
conventions; the discriminator byte is prefixed by the sender and
stripped by the receiver, so the lockstep substrate's `PACKET_SIZE = 12`
framing is untouched.

**This swap is the load-bearing architectural decision of PR 11.6.** The
existing 14 smokes must continue to pass against `P2PGgnetTransport`
(default-untouched path), AND a new smoke must pass against
`ServerGgnetTransport` + the actual server in `server/`. Both
implementations live side-by-side in `ggnet.ts`.

### 3.7 What does NOT change in PR 11.6

- `client/src/net/ggrsRuntime.ts` — unchanged. The lockstep substrate

- `client/src/game/combat.ts` — `dualPistolShoot` and `meleeSwing`

- `client/src/game/health.ts` — `applyDamage` and `tickRespawn`

### 3.9 Client-side damage prediction (added in this revision)

The original §3.4 / §2.2 flow says the shooter sees the bullet visual
locally but waits for `DamageBroadcast` (RTT/2 minimum) before any HP
change. **Every shipped competitive FPS shows the HP drop on the
shooter's screen immediately** — CS2, Valorant, Overwatch, Apex all do
"favor the shooter" prediction: shooter sees the HP drop locally,
server confirms or overrides, and a misprediction plays a "no damage"
correction animation.

**Plan change**: `damageBus.queue(event)` does TWO things, not one:

1. Send `DamageRequest` to the server (existing plan).
2. Optimistically apply `applyDamage(remoteController, ...)` LOCALLY
   on the shooter side, tagged with the request's `eventId`.

When `DamageBroadcast{originEventId = X}` arrives:
- If it matches our pending optimistic apply for `X`: confirm (no-op).
- If it disagrees (target already dead, amount different, rejected
  for fire-rate): revert the optimistic apply + play a "no damage"
  correction tracer on the HUD.

**Cost**: ~15 lines in `damageBus.ts`, plus a "pending optimistic
applies" map keyed by `eventId`. UI adds a 50ms "denied" tracer flash
on the shooter side for mispredicted events.

**Defensible in PR 11.6.D?** Yes — this is a UX fix, not a netcode
fix, and the predicted-vs-confirmed mismatch path is small. Carried
into 11.6.D's smoke (`client-damage-server-smoke.mjs` asserts the
shooter sees HP drop within 1 frame of pulling the trigger).

### 3.10 Tick rate target (added in this revision)

The original plan didn't specify a server tick rate or a client send
rate for `PositionUpdate` / `DamageRequest`. Without a target, these
default to "as fast as the runtime lets us" — which on a Tokio server
means 1000+ Hz, which on a browser tab means main-thread saturation.

**Plan change**:

- **Server simulation tick rate: 64Hz.** The server's `validate_and_relay`
  is event-driven (kicks on incoming `DamageRequest`), not tick-driven,
  so this number is mostly about `PositionHistory` insertion cadence
  for players who haven't fired recently. 64Hz ≈ 16ms per tick, well
  within budget for `HashMap<PlayerId, VecDeque<...>>` updates.
  Aligns with industry floor (CS2/Valorant are 128Hz; Overwatch 60Hz;
  64Hz is the standard "good enough for competitive but not elite" tick).
- **Client send rate for `PositionUpdate`: 32Hz** (every other server
  tick). Bandwidth at 14 bytes × 32Hz × 2 players in a 2-tab match
  = 896 B/s outbound per tab. Trivial.
- **Client send rate for `Ping`: 1Hz** (every 1s) for the sliding-window
  RTT average. 4 bytes × 1Hz = 4 B/s outbound. Trivial.

These are constant in `protocol/constants.ts` + `protocol/constants.rs`:

```typescript
export const TICK_RATE_HZ = 64;
export const POSITION_UPDATE_HZ = 32;
export const PING_HZ = 1;
```

**Cost**: 3 constants + the `sendPositionUpdate` cadence in
`gameSession.tick` (gated by a frame counter so we send every other
tick). ~10 lines.

## 6. Open questions for review

These are the calls **only you can make**, in priority order:

### Q1. **WebTransport-first or WebSocket-first?** — **RESOLVED: WebTransport-first**
PR 11.6.B's `tools/canary-server.sh` + smoke now ship with WebTransport
as the primary transport per §3.3 (revised). WebSocket is the
auto-fallback for networks that block QUIC. Alternative: WebSocket
first, which is what the original draft of this PR recommended — the
rejection is documented in §3.3 + `docs/PR-11.6-netcode-research.md` §C.

**My recommendation** (revised): WebTransport-first. Self-signed cert
cost is ~30 minutes, not 1-2 sessions, and removing PR 11.6.E
collapses the rollout from 5 sub-PRs to 4.

### Q2. **Matchmaker or hard-coded "DEVBX" room?**
PR 11.6.D's smoke needs both tabs in the same room. Options:
- (a) Both tabs share a hard-coded `roomId = "DEVBX"` (smoke-only).
  Spec-style matchmaking (`roomId = "DEVBX"` from URL or random on
  host) is a separate PR.
- (b) Add a minimal matchmaker endpoint (`POST /rooms` creates a
  room, `GET /rooms/<id>` polls existence). Two-tab smoke would
  hit the same `/rooms` endpoint.

**My recommendation**: (a). Smoke-friendliness wins; Phase 1's
matchmaker is a separate PR after 11.6.D.

### Q3. **Server-frame clock source?**
For PR 11.6.D, `DamageBroadcast.serverFrame` needs a clock. Options:
- (a) `tokio::time::Instant::now()` at server startup, monotonic across
  the process. Re-broadcast frames per damage event.
- (b) `server.nextDamageBroadcastNumber` counter, wraps at u32::MAX.

**My recommendation**: (a). Monotonic clock is universal and matches
the spec's "tick-driven" framing.

### Q4. **Whose eventId is canonical?**
The tab-issued `eventId` is the dedupe key on the tab side; the
server's `serverSeq` is the dedupe key on the server side. Q:
should we *also* send the server's `serverSeq` back to the tab? Q4
specifically: do we want bidirectional dedupe (tab's `eventId`
matched against server's echoed `originEventId`)?

**My recommendation**: yes — round-trips are cheap, dedupe is the
canonical Phase 4 anti-cheat concern.

### Q5. **Should PR 11.6 ship before the existing sim server gets a
`Disconnect` handling layer?**
Today, PR 11.5's pause-when-too-far-behind has a known honest
limitation: a `paused` tick drops the input that the cap fired on
(both clients drop symmetrically, no de-sync, but the input is lost).
PR 11.6 inherits this — if the server's damage broadcast doesn't fire
on a `paused` frame, the rising-edge is lost.

**My recommendation**: yes, ship PR 11.6 with this carry-over. The
fix is a follow-up that ties `paused: true` ticks to a "request
re-broadcast" wire packet from the server. Documented as
post-11.6.D follow-up.
