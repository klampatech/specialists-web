# PR 11.6 — FPS Netcode Industry Comparison

**Source**: Evo research session 2026-08-16, dispatched against PR #28 (`docs/pr11.6-plan`).
**Audience**: kyle + Evo, before deciding on the 5 open questions in PR 11.6 §6.

## TL;DR

The plan is sound directionally (server-auth-for-damage is correct, hybrid P2P+server is defensible at small player count). **Three items are flagged "revisit now" because they will produce user-visible "shitty netcode" symptoms if shipped as-is, and each is a small change**:

| # | Item | Cost | Why it's flagged now |
|---|---|---|---|
| 1 | **Position history / lag compensation on the server** | ~30 lines + a buffer | Without it, "shot didn't count" — the #1 netcode complaint in shooters |
| 2 | **WebTransport for the dev canary too** (not just prod) | swap `tokio-tungstenite` → `webtransport-rs`/Quinn in `server/Cargo.toml`; ~1 session | TCP head-of-line blocking masks real netcode bugs during dev |
| 3 | **Fire-rate / ammo validation on `damage_relay`** | ~15 lines | Day-one trivial cheat: unlimited damage requests, no anti-cheat needed |

Three more are "revisit in 11.6.E" (still on the same arc, lower blast radius): client-side damage prediction, interpolation buffer for remote players, tick rate target. The plan correctly defers reconnect / matchmaker / full anti-cheat.

## The reconciliation that matters

The research subagent flagged "no client-side damage prediction" assuming the plan shows the bullet but waits for the broadcast before any HP change. The plan doesn't explicitly say which it does — it's silent. Both interpretations are recoverable in the same code path (apply optimistically on shooter side, reconcile on broadcast), so this is a UX detail to nail down in 11.6.D, not a plan rewrite.

The "no rewind" finding is more important than the subagent's framing suggested. The plan's stated model is "server validates against current positions." But the server doesn't *have* current positions — the damage request carries no position data, only `sourcePlayerId/targetPlayerId/amount`. Two readings:

- **(a) Server joins the lockstep** — receives position updates per tick, validates against its own current world model. Requires the server to participate in the input stream too. Heavier but cleanly solves lag comp.
- **(b) Server stores a position history per player** — accepts position updates alongside damage requests, validates against `t_request − rtt/2 − interp_delay` snapshot. Lighter and the standard pattern.

The plan is currently silent on this. **(b) is the right answer for Phase 1** and is what every shipped FPS does. ~30 lines + a `VecDeque<(serverFrame, Position)>` per player.

## How the research ranked each open question

### Q1 — WebSocket-first or WebTransport-first

**Research verdict: WebTransport-first, even for dev.**

Subagent cited WebTransport's per-stream isolation (lost packet on `damageBroadcasts` doesn't block `inputs`) and showed browser support is universal in 2026. Even as a *dev-stack* concern: running your game loop over TCP means you discover netcode bugs that only show under QUIC, then have to debug them later in production.

**Plan recommendation (WebSocket-first)**: weak. WebSocket → WebTransport was "deferred to 11.6.E" partly because the spec treats WebSocket as "fallback for restricted networks." That's a *production* argument (firewall-restricted corporate networks, mobile carriers blocking QUIC). For dev and canary it doesn't apply. **Suggest Q1 answer changes to: WebTransport-first for dev + prod, WebSocket fallback only if WebTransport fails to connect (handled by transport auto-downgrade).** Same dev-loop velocity; no production re-architecture later.

**Cost**: `server/Cargo.toml` swaps `tokio-tungstenite` → `wtransport` (or `quinn`); `client/src/net/serverTransport.ts` uses browser `WebTransport` API instead of `WebSocket`. ~1 session shift (it was 11.6.E; moving it into 11.6.B adds ~1 session to 11.6.B, removes 11.6.E). Net zero, better outcome.

### Q2 — Matchmaker or hard-coded `roomId = "DEVBX"`

**Research verdict: agree with plan recommendation (a).** Matchmaker is a Phase 2 problem. For a 2-tab smoke, hard-coded room is correct. *No change.*

### Q3 — Server-frame clock source

**Research verdict: agree with plan recommendation (a) — `tokio::time::Instant` monotonic.** But the plan doesn't ask "do we *also* expose RTT to the client?" The research flags this as a missing dimension. **Add to plan §3.5 / wire format: include a `serverTime` echo in every `DamageBroadcast`, plus a separate `Ping`/`Pong` message pair (4 bytes each, monotonic clock).** Trivial cost; you need RTT for any future lag comp tuning even if you don't use it now.

### Q4 — Bidirectional eventId dedupe

**Research verdict: agree with plan recommendation (yes).** Cheap, useful for future anti-cheat. *No change.*

### Q5 — Ship with `paused`-tick input loss

**Research verdict: agree with plan recommendation (yes, document + table).** Phase 1 acceptance test is "best effort"; the fix is a separate `requestRebroadcast` wire packet — small PR but out of scope for 11.6. *No change.*

## The three "revisit now" items in detail

### 1. Position history on the server (lag compensation)

**Why this is the biggest single concern**: the subagent research is correct that "current position, no rewind" is the textbook anti-pattern. Even Valorant (which targets 16ms server frame) uses a 1-second history buffer for rewind. Without it, a target who moves laterally behind cover between the shooter's click and the server's validate is "not hit" — the player's screen says one thing, the HP says another.

**Recommended addition to plan §3.4 (server-side validation)**:

```rust
// server/src/position_history.rs (NEW, ~50 lines)
pub struct PositionHistory {
    frames: VecDeque<(ServerFrame, Position)>,
    retention: Duration, // ~1 second
}
impl PositionHistory {
    pub fn record(&mut self, frame: ServerFrame, pos: Position) { ... }
    pub fn snapshot_at(&self, t: ServerTime) -> Option<Position> {
        // find the entry with largest frame <= t
    }
}
```

Position updates flow as a new wire message (`PositionUpdate{u16 playerId, u16 frame, [f32;3] pos}` — 14 bytes). On `DamageRequest{...}`, server looks up target's position at `serverFrame - (clientRttMs / 2 / 16.67)`, validates the hit at *that* position using the weapon's hitscan math (which the server must now implement — ported from `client/src/game/combat.ts:dualPistolShoot`).

**This is the change the subagent undersold.** It moves us from "validate `source≠target, amount≤100`" to "actually validate the hit." Without it, the server's `damage_relay.rs` is a relay, not a validator — every player-trusted number crosses the wire unchanged. That's a server-auth boundary in name only.

**Cost**: ~1 session of work, plus a unit test fixture (mock position histories).

### 2. WebTransport for the dev canary

See Q1 above. Adds ~1 session to 11.6.B; removes 11.6.E entirely. Net zero.

### 3. Fire-rate / ammo validation on damage relay

**The trivial-cheat test**: open devtools, send `DamageRequest{source=0, target=1, source=fire, amount=255}` 100x/sec. Plan's validation rejects `amount > 100` but doesn't track *when* the player last fired. Result: 12-damage-per-tracer pistol fires as a 100-damage-per-frame cannon.

**Recommended addition to plan §3.4**:

```rust
// In Room:
last_fire_time: HashMap<(PlayerId, WeaponId), Instant>,
ammo: HashMap<PlayerId, AmmoState>,

// In validate_and_relay():
match req.source {
    Weapon::Fire => {
        let now = Instant::now();
        let last = self.last_fire_time.get(&(req.source, Weapon::Fire));
        if let Some(t) = last {
            if now.duration_since(*t) < FIRE_COOLDOWN { return None; }
        }
        self.last_fire_time.insert((req.source, Weapon::Fire), now);
    }
}
```

`FIRE_COOLDOWN` matches the client's local pistol cadence (look at `client/src/game/combat.ts` for the actual ms). 10-line change.

## "Revisit in 11.6.E" items (deferred, not dropped)

- **Client-side damage prediction** — when local shooter pulls the trigger, optimistically apply damage locally; reconcile on broadcast. UX fix, not a netcode fix.
- **Interpolation buffer for remote players** — 50-100ms buffer + lerp between snapshots. Already relevant for Phase 0's P2P rendering, not new to Phase 1.
- **Tick rate target** — 64Hz is the defensible floor for a 2026 FPS. Plan doesn't state one; pick 64 and document.

## Out of scope (correctly deferred)

- **Reconnect** — separate PR after 11.6.E.
- **Matchmaker** — separate PR after 11.6.E.
- **Full anti-cheat (movement rate, position plausibility, statistical anomaly detection)** — Phase 4. But the server-authority foundation lands now, so the surface exists for those checks.
- **Schema codegen (protobuf/flatbuffers)** — hand-rolled is fine at 4 messages × ~5 fields. *But fix the byte-count bug in `DamageBroadcast` (the plan says 17 bytes, the field `byte 14..17` inclusive is actually 18 bytes).*

## What I'd leave alone

These items from the original plan hold up under industry comparison **at small player count (2-4p)**:

- The hard-coded `roomId = "DEVBX"` for the smoke (Q2). For the dev-box two-tab smoke.
- The monotonic clock choice (Q3a) — `tokio::time::Instant` monotonic. Universal.
- Bidirectional eventId dedupe (Q4) — round-trips are cheap; useful for future anti-cheat.
