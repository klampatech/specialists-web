## 1. Why this PR is the next thing post-PR 11.6.D

PR 11.6.D (squash `e9ac169`, MERGED 2026-08-18) shipped **server-authoritative
damage**. Damage application now flows through `validate_and_relay` → broadcast
→ `applyBroadcast`; lag-comp rewind exists on the server; client-side damage
prediction works (the §3.9 "favor the shooter" UX); fire-rate / ammo gates are
enforced server-side. **Movement + bullet-time + visual state still flow through
the legacy `ggrsRuntime.ts` lockstep substrate.**

That substrate was sized for 2-4 players (Phase 0's target). At
Kyle's clarified **~24 players per room** production target, it doesn't scale
(see `docs/PR-11.6-plan.md` §1.1, which carries forward unchanged):

- WebRTC mesh caps at ~10 peers per browser tab → 24 players means
  276 simultaneous peer connections per tab → browsers fail long before
  that.
- Even if WebRTC were replaced by SFU/MCU, 24 clients × 60Hz × 12-byte
  input packets = ~17KB/s outbound per player for inputs alone. The
  whole point of P2P lockstep (avoid the server bottleneck) is gone.
- Game-state divergence across 24 clients grows fast — even with
  deterministic simulation, *visual* jitter from network variance
  compounds with player count.

**The industry answer** (every shipped competitive shooter past ~8 players:
CS2, Valorant, Apex, Overwatch, Quake Champions): **server is the source of
truth for movement AND damage**. Clients predict locally + reconcile on server
snapshots. WebRTC stays for low-latency voice (Phase 5+) but not for game state.

PR 11.7 is the move from "hybrid P2P-lockstep-for-movement +
server-auth-for-damage" to "fully server-authoritative, CS2/Valorant-shaped
netcode." This is the **largest single PR in the Phase 1 chain** — the
estimate in `docs/PR-11.6-plan.md` §5.3 was 4-5 sessions + ~500-1000 lines,
and that's the floor.

### 1.1 What PR 11.7 is not doing

To keep review cost + regression risk bounded:

- **No anti-cheat** beyond the trivial-cheat gates already in
  `damage_relay` (fire-rate, ammo, eventId monotonicity). Movement-rate
  plausibility, position-jump plausibility, and statistical anomaly
  detection are a separate PR (PR 11.10 per `docs/PR-11.6-plan.md` §5.3).
- **No matchmaker**. Hard-coded `roomId = "DEVBX"` stays for the smoke
  surface. Matchmaker is PR 11.9.
- **No Hetzner production deploy**. PR 11.11.
- **No reconnect handling**. The "drop player + emit `playerLeft`"
  disconnect handling from PR 11.6.D carries forward unchanged; full
  reconnect is a separate PR after the matchmaker ships.
- **No client-side damage prediction rewrite**. PR 11.6.D's
  `damageBus.pendingApplies` + 4-path `applyBroadcast` is correct and
  verified. PR 11.7 doesn't touch it.

### 1.2 The CS2/Valorant reference architecture (carried forward from PR 11.6 §1.2)

The seven architecture choices from `docs/PR-11.6-plan.md` §1.2, restated here
with what PR 11.7 actually does (not what 11.6 deferred):

1. **Server is the source of truth for movement AND damage.**
   Damage is done (11.6.D). Movement is PR 11.7.B (snapshot generator +
   server-side physics tick).
2. **Clients predict locally.** Run the simulation forward using the
   player's own inputs between server snapshots. Zero perceived latency
   on the local player. PR 11.7.C (client prediction module).
3. **Server sends authoritative snapshots at 20-64Hz.** PR 11.7.B
   (snapshot generator + `Snapshot` wire type replaces per-player
   `PositionUpdate`).
4. **Clients reconcile on snapshot receipt.** Compare predicted state
   to authoritative state; re-simulate from last server-confirmed
   frame if there's drift. PR 11.7.C (reconciliation logic in
   `gameSession.ts`).
5. **Lag compensation on the server.** When shooter fires, server
   rewinds all other players to where they were when shooter clicked
   (~rtt/2 + interpolation delay ago). Done (11.6.D, `damage_relay.rs`).
6. **Remote players are interpolated, not predicted.** Each client
   keeps a 100-150ms buffer of remote-player snapshots and lerps
   between them. PR 11.7.C (interpolation buffer).
7. **WebTransport (QUIC) for the wire.** Done (11.6.B).

**PR 11.7 ships items 2, 3, 4, 6.** Items 1, 5, 7 are already in place.

### 1.3 The PR 11.6 seams that paid off (and the ones that need rework)

PR 11.6 deliberately added four seams (per §1.2 of that plan) so PR 11.7
would be additive rather than a rewrite. Audit:

| Seam (from PR 11.6 §1.2) | Status | 11.7 use |
|---|---|---|

| `Room.inputs_buffer: HashMap<PlayerId, VecDeque<(ServerFrame, EncodedInput)>>` | ✅ Shipped in `server/src/session.rs`. | 11.7.B reads from this on each server tick. |

snapshot fan-out at 20Hz (see `docs/PR-11.6-plan.md` §3.10.1 bandwidth
math). At 2-tab smoke this is invisible; at 24p it's 21.5 KB/s/server
outbound for position broadcasts alone. PR 11.7.B's snapshot
generator replaces it; until then, the bandwidth is wasted but
correct.

## 2. What "server-authoritative movement" actually means

### 2.1 Current movement flow (post-PR 11.6.D, before 11.7)

Both clients run **identical Havok WASM physics** with **identical inputs** —
deterministic lockstep. `client/src/net/ggrsRuntime.ts` collects inputs from
both tabs (via WebRTC data channels), submits each tick to ggrs, advances the
shared frame counter. Each tab runs the Havok physics locally on the same
inputs → identical world state. Visual jitter from WAN latency compounds
because the frame counter falls behind the wall clock for the lagging tab,
and the chase camera + interpolation can't fully hide the gap.

This worked under LAN / Tailscale / <50ms RTT. It broke under WAN because:

1. **Frame-counter desync**: the lagging tab pauses (`paused: true` frame
   per PR 11.5's `ROLLBACK_CAP_FRAMES = 8`) when too far behind the peer's
   local frame. Two tabs in lockstep pause symmetrically (no de-sync), but
   the pause is visible as a stutter.
2. **No rollback**: a missed input gets resubmitted on the next round, but
   the deterministic simulation doesn't roll back to re-apply — it
   forward-fills. Visual desync accumulates.
3. **No client-side prediction**: the local player's character is locked
   to the ggrs frame counter; if the frame counter pauses (PR 11.5 cap),
   the character doesn't move even though the local input is being
   processed.
4. **No server world model**: the server only knows HP + damage + ammo
   state (per `server/src/session.rs`). It doesn't know player positions
   or velocities. Damage's lag-comp rewind works because
   `PositionHistory::snapshot_at(t)` exists, but the server can't
   validate "did this player actually move from A to B" because there's
   no server-side physics.

### 2.2 PR 11.7's new flow

```
┌──────────────┐  InputsServer(per tick)  ┌──────────────┐  Snapshot(20Hz) ┌──────────────┐
│  Tab A       │ ────{frame,inputs}───▶   │              │ ──{frame,        │  Tab B       │
│  client-side │                          │   Game       │   [PlayerState   │  client-side │
│  predictor   │ ◀────StateAck───         │   Server     │    × N],         │  predictor + │
│  + reconciler│                          │ (Tokio +     │    nextFrame}──▶ │  reconciler  │
└──────────────┘                          │  WebTransport│                  └──────────────�
                                          │  + Rust tick │   ┌──────────────┐
                                          │  loop + Rapier│  │  Tab A       │
                                          │  or Havok)   │   │  (also gets  │
                                          │              │ ◀─┤  snapshot)   │
                                          └──────────────┘   └──────────────┘
```

Sequence per server tick (64Hz):

1. Server drains `Room.inputs_buffer` for the current tick.
2. Server advances its physics simulation by 1/64s for every connected
   player using the drained inputs. (Physics choice: see §3.1.)
3. Server constructs a `Snapshot{serverFrame, [PlayerState × N]}` where
   `PlayerState = {playerId, position, velocity, yaw, pitch, hp, ammo,
   weaponState, isFiring, bulletTime}`.
4. Server broadcasts `Snapshot` to all clients (20Hz cadence — every 3.2
   ticks; configurable via `SNAPSHOT_RATE_HZ`).
5. Client's predictor receives `Snapshot`, compares to its predicted
   local state, reconciles if there's drift, applies remote-player
   interpolation buffer advance.

Sequence per client frame (60Hz local, decoupled from server 64Hz):

1. Client receives local input (WASD, mouse, fire/melee buttons).
2. Client applies input to its **predicted** physics simulation
   (Havok WASM, same as today — but local-only, not lockstep).
3. Client sends `InputsServer{localFrame, inputs, inputSeq}` to server
   via `submitLocalInput` (the §1.3 seam).
4. Client buffers the input locally tagged with `inputSeq` for later
   reconciliation.
5. On `Snapshot{serverFrame}` arrival: compare predicted state to
   snapshot state. If drift > `RECONCILIATION_THRESHOLD_M`
   (default 0.1m), re-simulate from last server-confirmed frame forward
   using buffered inputs. If drift <= threshold, no-op.
6. Apply the snapshot's remote-player states to the interpolation buffer.
   The buffer holds the last 100-150ms of snapshots; render uses
   `interpolate(buffer[latest - INTERPOLATION_DELAY_FRAMES], nowMs)`.

### 2.3 Why this works without breaking damage

- **Damage is already server-authoritative** (PR 11.6.D). Damage's
  `validate_and_relay` reads `req.frame` (now derived from the server
  frame, not the lockstep frame) + the shooter's historical
  `PositionHistory::snapshot_at(req.frame - lag_frames)` to do
  lag-comp. The target's `PositionHistory` is now fed by the server
  physics tick (PR 11.7.B), not by the client's `PositionUpdate`
  packets. **The damage path is unchanged in shape** — only the
  source of the position data moves.
- **Inputs flow server-side from day one** because of PR 11.6's `0x06`
  discriminator seam. PR 11.7.B flips `submitLocalInput` to actually
  send them; PR 11.6.D's "buffered but unused" path is consumed.
- **Wire format extensions only** — new `Snapshot`, `StateAck`,
  `InputSeq` discriminator bytes. Damage wire bytes are unchanged.

### 2.4 Determinism contract (extended)

**Pre-PR-11.6 rule (still applies for movement/combat visuals, but no
longer requires cross-client determinism)**:
*Every physics-affecting input is a frame-aligned integer. Never read
`Date.now()` inside the tick.*

**PR 11.6.D addition (still applies for damage)**:
*Damage HP on each client equals the sum of `DamageBroadcast.amount`
applied in receive order, with starter HP of 100. Server is the source
of truth; client-side prediction reconciles on broadcast.*

**PR 11.7 addition (movement)**:
*Each client's locally-predicted player position equals the server's
authoritative position for that player, up to `RECONCILIATION_THRESHOLD_M`
(0.1m default). Larger drift triggers reconciliation: re-simulate from
last server-confirmed state forward using buffered inputs.*

**Remote players are NOT predicted.** Each client keeps a 100-150ms
buffer of remote-player snapshots and lerps between the two adjacent
snapshots for render. The interpolation delay is the cost of "smooth
remote visuals" vs. "snappy local input" — industry standard tradeoff.

Edge cases called out explicitly:
- If a `Snapshot` arrives after the local predicted player crosses
  `RECONCILIATION_THRESHOLD_M`, reconciliation re-simulates from the
  snapshot's state forward. Visually a small "rubber band" snap —
  bounded by `MAX_RECONCILIATION_SNAP_DISTANCE_M` (default 2m; clamp
  the visual snap distance so a 100ms desync doesn't teleport the
  character across the map).
- If a `Snapshot` is dropped (UDP packet loss on WebTransport), the
  next `Snapshot` carries the same player's state at a later frame —
  no re-request needed. The interpolation buffer skips the gap
  (renders the two adjacent snapshots across the gap, slightly
  smoothed).
- If the client falls behind by more than `MAX_SNAPSHOT_AGE_MS`
  (default 500ms = 10 snapshots at 20Hz), the client requests a
  full-state resync via a new wire type `StateResyncRequest`
  (see §3.5).

## 3. Architecture

### 3.1 Server physics authority — the BIG open question

Two implementation paths:

| Concern | Port Havok math to Rust | Adopt Rapier WASM as a server lib |
|---|---|---|
| Engineering cost | 3-4 sessions (reimplement capsule, gravity, ground detection, jump physics in Rust; match Havok WASM byte-by-byte) | 1-2 sessions (add `rapier3d` crate, call from server tick) |
| Determinism | Requires per-tick deterministic math (the WASM Havok is already deterministic; porting must preserve byte-equality) | Rapier has a `deterministic` feature flag; need to verify it matches Havok WASM's behavior at the bit-level for visual consistency |
| Latent physics bugs | High risk: Havok is a black box, porting means re-discovering edge cases (e.g., wallrun cooldown logic from PR 11.2.3, jump condition `vy ≤ 0` from PR 11.5) | Low risk: Rapier is a well-known physics engine, but its behavior diverges from Havok's in subtle ways (collision response curves, friction models) |
| Future flexibility | None — Havok is what Havok is | High — Rapier has open-source ecosystem (3D physics, soft body, vehicles) |
| Bundle weight | None on server | Rapier WASM is ~500KB; pure-Rust Rapier is ~3MB compiled. Both fit easily. |

**My recommendation**: **Rapier WASM as a server lib** — specifically,
`rapier3d` Rust crate (the native Rust port, not the WASM build) compiled
into the existing `server/` binary. The client keeps Havok WASM (no change
to client bundle); the server runs Rapier Rust. They do NOT need to be
bit-equivalent because:

1. The server is the source of truth for positions + velocities. The
   client doesn't run server-authoritative physics locally — it runs
   Havok WASM for **predicted local input** only, then reconciles to
   the server's Rapier state on snapshot receipt.
2. Visual jitter from Havok-Rapier divergence is bounded by
   `RECONCILIATION_THRESHOLD_M` (0.1m default). Sub-threshold drift is
   invisible; super-threshold drift triggers reconciliation (visible
   snap, also bounded by `MAX_RECONCILIATION_SNAP_DISTANCE_M`).

This is the cleanest answer to "do we need bit-equivalence?" — **no, we
need convergence, not bit-equality**. The lockstep substrate's
bit-equivalence requirement came from "both clients run identical sim
on identical inputs." Server-authoritative substrate doesn't have
that requirement at all; the client runs its own sim, the server
runs its own, reconciliation handles the divergence.

**Cost**: add `rapier3d` to `server/Cargo.toml`; ~80 lines of server
ticking code (`server/src/physics.rs` + integration into the existing
tick loop in `server/src/main.rs`).

**Risk**: the predicted-vs-authoritative visual mismatch is real but
bounded. Worst-case user experience is a 0.5m rubber-band every 50ms
under high WAN latency — visible but not game-breaking. We can
verify with the dev-box two-tab WAN-throttle test (PR 11.6.D's
synthetic 200ms throttle is the natural test environment).

**This is open question Q1 — needs your call.**

### 3.4 Server architecture (after PR 11.7.B lands)

```rust
// server/src/main.rs (sketch — not for merge, for architecture only)

#[tokio::main]
async fn main() -> anyhow::Result<()> {
    // ... existing WebTransport + WebSocket listeners + room registry ...

    let rooms = Arc::new(RwLock::new(HashMap::<RoomId, Room>::new()));

    // NEW in 11.7.B: physics tick loop per room.
    for (room_id, room) in rooms.write().await.iter_mut() {
        tokio::spawn(physics_tick_loop(room.clone()));
        tokio::spawn(snapshot_generator_loop(room.clone()));
    }
}

async fn physics_tick_loop(room: Arc<RwLock<Room>>) {
    let mut interval = tokio::time::interval(Duration::from_micros(15_625)); // 64Hz
    loop {
        interval.tick().await;
        let mut room = room.write().await;
        // 1. Drain inputs_buffer for this tick
        let inputs = room.drain_inputs_for_tick(room.next_server_frame);
        // 2. Step Rapier physics for every connected player with their inputs
        room.physics.step(inputs);
        // 3. Record post-physics position into PositionHistory (fed by server, not client)
        for player in room.players.values() {
            room.position_history
                .entry(player.id)
                .or_default()
                .record(room.next_server_frame, player.physics.position());
        }
        // 4. Increment server frame counter
        room.next_server_frame += 1;
    }
}

async fn snapshot_generator_loop(room: Arc<RwLock<Room>>) {
    let mut interval = tokio::time::interval(Duration::from_millis(50)); // 20Hz
    loop {
        interval.tick().await;
        let mut room = room.write().await;
        let snapshot = Snapshot {
            server_frame: room.next_server_frame,
            players: room.players.values().map(PlayerState::from).collect(),
        };
        let encoded = snapshot.encode();
        room.broadcast(&encoded).await; // fan out to all room connections
    }
}
```

### 3.5 Wire protocol additions

The PR 11.6 discriminator table (in `docs/PR-11.6-plan.md` §3.5) gets
new entries. **Important pre-emptive note**: PR 11.6.D shipped
`DamageReject` at discriminator byte `0x07`; this plan reserves
`0x07` for `Snapshot`. The collision is resolved by PR 11.7.B by
bumping `DamageReject` to `0x0C` (outside the reserved 0x07-0x0B
range). See "Discriminator reorganization" callout below.

```
byte 0 == 0x06 → inputsServer (PR 11.6.C; the per-tab input packet,
                  server-routed via `Room.inputs_buffer`)
byte 0 == 0x07 → snapshot (variable length — header + N × PlayerState)
                  [PR 11.6.D had DamageReject here; bumped to 0x0C
                   to free 0x07 for Snapshot in PR 11.7.B]
byte 0 == 0x08 → stateAck (8 bytes — client → server: {clientFrame, lastServerFrameAcked})
byte 0 == 0x09 → inputSeq (4 bytes — client → server: monotonic inputSeq counter; for ordering)
byte 0 == 0x0A → reloadRequest (6 bytes — client → server: {frame, playerId} — PR 11.7.E)
byte 0 == 0x0B → stateResyncRequest (4 bytes — client → server: {playerId} — for clients that fell behind by > MAX_SNAPSHOT_AGE_MS)
byte 0 == 0x0C → damageReject (5 bytes — server → client: {eventId, reason})
                  [moved from 0x07 in PR 11.7.B — see callout]
```

**Discriminator reorganization (PR 11.7.B implementation finding)**:
The plan-as-written (§3.5 above) had two contradictory statements:
(a) "`0x07-0x0B` is reserved for new wire types" and (b) "PR 11.6.D
shipped `DamageReject` at `0x07`." Both couldn't be true. PR 11.7.B's
implementation resolved this by bumping `DamageReject` to `0x0C`
(outside the reserved range), giving `0x07` to `Snapshot` as planned.
**Migration impact**: PR 11.6.D clients connecting to a PR 11.7.B
server will receive `DamageReject` at `0x0C` (new value), look it up
in their `protocol/damage.ts` table (still says `0x07`), and silently
warn+drop as "unknown discriminator." The damage flow itself still
goes through `validate_and_relay`; only the rejection notification is
lost on the legacy client. Acceptable per the one-PR migration window
pattern, but documented here so future reviewers understand the dual
breaking change (this `DamageReject` bump + the planned `0x06
InputSeq` trailer deferred to 11.7.C).

**Snapshot wire format** (header + N players):

```
Snapshot on the wire (variable length — header 8 bytes + N × 22 bytes per player):
  byte 0      discriminator 0x07
  byte 1..4   serverFrame (u32 BE)
  byte 5..6   playerCount (u16 BE — up to MAX_PLAYERS_PER_ROOM = 24)
  byte 7      flags (u8 — bit 0 = isAuthoritativeFrame, bit 1 = fullResync)
  byte 8..    PlayerState[playerCount] (each 22 bytes — see below)

PlayerState on the wire (22 bytes):
  byte 0..1   playerId (u16 BE)
  byte 2..5   positionX (f32 BE)
  byte 6..9   positionY (f32 BE)
  byte 10..13 positionZ (f32 BE)
  byte 14..17 velocityMagnitude (f32 BE — for client-side interpolation)
  byte 18..19 yaw (u16 BE — same encoding as PR 11.1's input yaw)
  byte 20..21 pitch (u16 BE — same encoding as PR 11.3's input pitch)
  // hp/ammo/weaponState/isFiring/bulletTime carried in follow-up entries if/when
  // server-authoritative state for those becomes meaningful. PR 11.7.B is position+yaw+pitch only.
```

**Bytes-on-wire at 24p**: 8 (header) + 24 × 22 (players) = 536 bytes per
`Snapshot`. At 20Hz, 10.7 KB/s/server outbound. Down from 21.5 KB/s for
per-player `PositionUpdate` at 32Hz (PR 11.6.D's pre-snapshot path) —
**2x bandwidth reduction**. Matches the §3.10.1 bandwidth math.

**StateAck wire format** (8 bytes — client → server, every Nth tick to
keep server's `lastAckedFrame[playerId]` fresh):

```
StateAck on the wire (8 bytes):
  byte 0      discriminator 0x08
  byte 1..4   clientFrame (u32 BE — local predicted frame counter)
  byte 5..7   lastServerFrameAcked (u32 BE — most recent Snapshot.serverFrame the client has fully reconciled)
```

Server uses `lastAckedFrame[playerId]` for two things:
1. **Input ack**: when all players have acked frame N, server can trim
   `inputs_buffer` history past frame N (memory bound).
2. **Lag-comp rewind tuning**: if a player's ack is consistently 3+ frames
   behind the server, that player is high-latency — extend their
   lag-comp rewind budget by N frames (the existing PR 11.6.D
   `req.frame.saturating_sub(lag_frames)` math handles this naturally;
   the ack is just the data source for "how far behind are they").

**InputSeq wire format** (4 bytes — client → server, piggybacked on the
existing `0x06 InputsServer` packet as a 4-byte trailer):

```
InputsServer on the wire (17 + 4 = 21 bytes — PR 11.6.B's 17-byte body + 4-byte inputSeq trailer):
  byte 0      discriminator 0x06
  byte 1..4   frame (u32 BE — same as ggrsRuntime.ts FRAME_HEADER_SIZE)
  byte 5..16  encoded input (12 bytes — same as INPUT_SIZE = 12)
  byte 17..20 inputSeq (u32 BE — monotonic counter, used for snapshot ack matching)
```

PR 11.6.B's `0x06 InputsServer` is currently 17 bytes; PR 11.7.B
extends it to 21 bytes. **This is a wire-format breaking change** for
clients on PR 11.6.D connecting to a server on PR 11.7.B. Mitigation:
the server detects the short form (17 bytes) and rejects with a
"please update" warning; the client-side error surfaces as a
disconnected HUD chip. The migration window is one PR cycle.

**StateResyncRequest wire format** (4 bytes — for clients that fell
behind by > `MAX_SNAPSHOT_AGE_MS`):

```
StateResyncRequest on the wire (4 bytes):
  byte 0      discriminator 0x0B
  byte 1..2   playerId (u16 BE)
  byte 3      reserved (u8 — 0)
```

Server responds by sending a `Snapshot` with `flags.fullResync = 1`
containing the full state (not a delta). Client uses this as a "start
fresh" signal — clears interpolation buffer, resets predictor's
reconcile-from-frame to the resync's `serverFrame`.

### 3.7 Server-side fire-rate / ammo validation (extends PR 11.6.D §3.4.2)

`server/src/damage_relay.rs::validate_and_relay` enforces

  reload-duration cooldown (1.5s per `client/src/game/combat.ts`).
- `ammo: HashMap<PlayerId, u8>` — current magazine ammo (12 per magazine

- `max_ammo: HashMap<PlayerId, u8>` — reserve ammo (separate from

The reload keybind (R) sends `ReloadRequest{playerId, frame}` to the

- Player has reserve ammo > 0.
- Player isn't already reloading.
- Player isn't dead.

On all gates pass: start reload (record `last_reload_start`), after

This is the same shape as `validate_and_relay`; ~30 lines of code.

### 3.8 Client-side prediction (PR 11.7.C, the load-bearing piece)

`client/src/net/predictor.ts` (NEW, ~400 lines):

```typescript
// Sketch — not for merge, for architecture only.

export class Predictor {
  private localInputs: Map<localFrame, EncodedInput> = new Map();
  private lastServerFrame: number = -1;
  private reconcileFromFrame: number = -1;
  private predictedState: PlayerState = /* current Havok character state */;

  /**
   * Called every local tick (~60Hz) BEFORE rendering.
   * Runs Havok WASM forward for the local player using locally-buffered inputs
   * since last reconcileFromFrame. Updates predictedState.
   */
  tick(localFrame: number, nowMs: number) {
    if (this.reconcileFromFrame < 0) return; // not yet initialized
    // 1. Drain inputs for frames (reconcileFromFrame, localFrame] from localInputs
    const inputs = drainInputs(this.localInputs, this.reconcileFromFrame, localFrame);
    // 2. Step Havok forward N times (one per drained input)
    for (const input of inputs) {
      this.predictedState = havokStep(this.predictedState, input);
    }
  }

  /**
   * Called on every Snapshot arrival.
   * Compares snapshot's local-player state to predictedState; if drift exceeds
   * RECONCILIATION_THRESHOLD_M, re-simulate forward.
   */
  onSnapshot(snapshot: Snapshot, nowMs: number) {
    const localInSnapshot = snapshot.players.find(p => p.playerId === this.localPlayerId);
    if (!localInSnapshot) return;

    const drift = distance(this.predictedState.position, localInSnapshot.position);
    if (drift > RECONCILIATION_THRESHOLD_M) {
      // Reconciliation: re-simulate from lastServerFrame forward
      this.predictedState = localInSnapshot;
      this.reconcileFromFrame = snapshot.serverFrame;
      const bufferedInputs = drainInputs(this.localInputs, snapshot.serverFrame, this.localFrame);
      for (const input of bufferedInputs) {
        this.predictedState = havokStep(this.predictedState, input);
      }
      // Clamp the visual snap distance — never let reconciliation teleport by > MAX_SNAPSHOT_SNAP_DISTANCE_M
      const snapDistance = distance(this.preSnapState.position, this.predictedState.position);
      if (snapDistance > MAX_RECONCILIATION_SNAP_DISTANCE_M) {
        // Hard clamp: snap to the snapshot's position, drop predicted inputs
        this.predictedState = localInSnapshot;
        this.reconcileFromFrame = snapshot.serverFrame;
      }
      this.reconciliationCount += 1;
    }
    this.lastServerFrame = snapshot.serverFrame;

    // Ack: every Nth snapshot, send a StateAck so server can trim inputs_buffer
    if (snapshot.serverFrame % 3 === 0) {
      this.transport.sendStateAck({ clientFrame: this.localFrame, lastServerFrameAcked: snapshot.serverFrame });
    }
  }

  /**
   * Records the local input for the current local frame.
   * Called by gameSession.tick() before sending to server.
   */
  recordLocalInput(localFrame: number, input: EncodedInput) {
    this.localInputs.set(localFrame, input);
    // Trim old inputs past lastServerFrame (server no longer needs them)
    if (this.localInputs.size > MAX_LOCAL_INPUT_BUFFER) {
      const oldestFrame = Math.min(...this.localInputs.keys());
      if (oldestFrame < this.lastServerFrame) {
        this.localInputs.delete(oldestFrame);
      }
    }
  }
}
```

### 3.9 Remote-player interpolation buffer (PR 11.7.C)

`client/src/net/interpolator.ts` (NEW, ~120 lines):

```typescript
export class Interpolator {
  private buffers: Map<playerId, RingBuffer<Snapshot>> = new Map();

  /**
   * Called on every Snapshot arrival.
   * Pushes the snapshot into each remote player's ring buffer (100-150ms deep).
   */
  onSnapshot(snapshot: Snapshot) {
    for (const player of snapshot.players) {
      if (player.playerId === this.localPlayerId) continue;
      const buffer = this.buffers.get(player.playerId) ?? new RingBuffer(8); // 8 snapshots = 400ms at 20Hz
      buffer.push(snapshot);
      this.buffers.set(player.playerId, buffer);
    }
  }

  /**
   * Called every render frame.
   * Returns the interpolated remote-player state for the render timestamp.
   * Uses INTERPOLATION_DELAY_FRAMES snapshots ago (default 2 = 100ms at 20Hz).
   */
  getInterpolatedStates(renderTimestampMs: number, currentSnapshot: Snapshot): PlayerState[] {
    const targetTime = renderTimestampMs - INTERPOLATION_DELAY_MS;
    const result: PlayerState[] = [];
    for (const player of currentSnapshot.players) {
      if (player.playerId === this.localPlayerId) continue;
      const buffer = this.buffers.get(player.playerId);
      if (!buffer || buffer.length < 2) {
        // Not enough history; render current snapshot directly
        result.push(player);
        continue;
      }
      // Find the two snapshots bracketing targetTime
      const [older, newer] = findBracketingSnapshots(buffer, targetTime);
      const t = (targetTime - older.serverTimestampMs) / (newer.serverTimestampMs - older.serverTimestampMs);
      result.push(lerpPlayerState(older, newer, t));
    }
    return result;
  }
}
```

### 3.13 Coyote-time parity (Rapier ↔ Havok) — 11.7.B

**Why this section exists**: Rapier and Havok model ground contact
differently. Havok uses a "support point" concept where a capsule
contact persists ~2 frames past the geometric ledge edge (empirical
observation from PR 11.2.3 wallrun cooldown work + the standard
Source-engine coyote-time window). Rapier uses a single contact
manifold — ground state flips to `false` the instant the capsule
center crosses the edge (1 frame, not 2).

Without parity handling, every coyote-frame jump produces
reconciliation drift:

- Havok client predicts "jump succeeded" (within coyote window).
- Rapier server rejects the jump (ground contact already lost).
- Reconciler sees ~5cm vertical drift + downward velocity on the
  predicted position vs authoritative. Snap applies, player appears
  to "fall through" the jump animation for 1-2 frames.

Worse case (rarer): Rapier server's `grounded` flips true → false
between `frame - 1` and `frame` from a ledge edge, but the rotation
of the capsule during the wallrun leaves a residual "support
manifold" that Rapier registers as `grounded = true` at frame N.
Havok client already flipped to `grounded = false` at frame N-1.
Reconciler snaps player UP to the ledge — visible as "stuck to
ledge" glitch.

**Fix**: server-side coyote-time grant in
`server/src/physics.rs::apply_jump`. The server tracks
`last_grounded_frame: HashMap<PlayerId, u64>` (updated every tick
where the Rapier contact manifold says `grounded = true`). On jump
request:

```
if !grounded_now                                          // Rapier says not grounded
   && grounded_prev_frame                                 // Havok prediction agreed with last tick
   && frame - last_grounded_frame <= COYOTE_FRAMES       // grace window
   && inputs.jump_pressed {
    // grant the jump — matches Havok's local prediction
    body.set_linvel(Vec3::new(vx, JUMP_IMPULSE, vz), true);
    last_grounded_frame = frame - COYOTE_FRAMES;          // burn the grace
}
```

`COYOTE_FRAMES = 2` (matches Havok's empirical 2-frame support
persistence at 60Hz client tick). Wallrun start uses a SEPARATE gate
(`WALLRUN_COYOTE_FRAMES = 1` per PR 11.2.3 — wallrun has a tighter
window because wall-sticking is more sensitive to float).

**Client side**: unchanged. Havok prediction continues to grant
coyote-time jumps locally; server's grant matches. Reconciler sees
zero drift on the coyote frame. **No 1-frame snap on ledge jumps.**

**Constants added** (`server/src/constants.rs`):
- `COYOTE_FRAMES = 2`
- `WALLRUN_COYOTE_FRAMES = 1`
- `JUMP_IMPULSE = 5.5` (matches `client/src/game/combat.ts` constant)

**Smoke**: `server/tests/session_canary.rs::coyote_time_grants_jump`
(server-only, no client). Scripted sequence: player walking off a
ledge, Rapier sets `grounded_at(N) = true`, `grounded_at(N+1) =
false`, inputs.jump_pressed at N+1 → assert Rapier applies
`JUMP_IMPULSE`. Plus: `coyote_time_deny_after_window` — jump at
`frame - last_grounded_frame > 2` → assert denied.

### 3.14 Hitscan-mid-air edge case (Rapier-history rewound target) — 11.7.B

**Why this section exists**: PR 11.6.D's `validate_and_relay`
already uses `PositionHistory::snapshot_at(req.frame - lag_frames)`
for lag-comp rewinds. Pre-11.7, `PositionHistory` was fed by client
`PositionUpdate` packets (32Hz, 31.25ms resolution). With PR 11.7.B,
`PositionHistory` is fed by the Rapier physics tick (64Hz per
`TICK_RATE_HZ`). The resolution is finer, but four new edge cases
appear because Rapier's history is now the source of truth for the
target's position at the rewind frame.

**Edge case 1 — History resolution when physics tick skipped**:
If the Rapier step() call exceeds its 15.6ms budget (slow frame),
the tick is dropped for that cycle. `PositionHistory::record` is
not called for that frame. `snapshot_at(t)` returns the largest
recorded frame `<= t`. For `t = N` where N was a dropped frame, we
return frame N-1's position — off by 15.6ms. A target moving at
5 m/s covers ~8cm in that time, well inside the 0.5m
`target_radius`, but on the edge of "passed through thin target."

**Fix**: `PositionHistory::record` stores every tick (64Hz), but
the underlying `VecDeque` holds every OTHER frame (32Hz storage).
`snapshot_at(t)` snaps to the nearest stored frame within ±15ms of
`t`. Same memory cost as 32Hz storage, same resolution as 64Hz
recording. Net cost: ~24 players × 32 frames × 40 bytes = ~30KB per
room. Implementation: ~10 lines in `position_history.rs`.

**Edge case 2 — Capsule orientation drift during rewind**:
Rapier's capsule yaw at frame N may lag the actual rotation by 1
frame (Rapier updates the capsule's kinematic body rotation based
on the previous tick's angular velocity). Client Havok has the
correct yaw at frame N (Havok updates the capsule rotation
immediately on input). The hitscan cone aim in
`validate_and_relay` uses the target's position only, not its
yaw, so this doesn't affect hit detection directly. But the
client's predicted view of the target may show it facing direction
A while the server's rewind has it facing direction A-1frame. Visible
only if the shooter is tracking the target's facing direction for
flank bonuses (PR 11.7.E territory — no flank bonuses planned).

**No fix needed for 11.7.B**; document in case future mechanics
need it.

**Edge case 3 — Chest-position Y offset**: `dual_pistol_hit`
elevates the aim point via `chest_position(capsule_centre)` to
match where the head hitbox is in `client/src/game/combat.ts`.
Rapier's capsule origin is the geometric center (matches Havok).
Smoke asserts the Y-offset matches within 1mm — if Rapier uses a
different anchor (e.g. feet), the hit Y-offset shifts by half the
capsule height and the smoke fails loudly.

**Edge case 4 — Replay attack at frame N**:
Malicious client sends `DamageRequest{req.frame = N}` where N is
far in the past, triggering a rewind through stale history. PR
11.6.D's `validate_and_relay` already rejects rewinds older than
`MAX_REWIND_FRAMES = 30` (per `damage_relay.rs` constants). No
change for 11.7.B.

**Smoke**: `server/tests/session_canary.rs::hitscan_rewinds_through_rapier_history_mid_air`.
2p room. Target A static on ground. Target B mid-air at frame N via
Rapier-applied jump impulse (no client PositionUpdate). Shooter
fires DamageRequest at frame N with 50ms lag. Server rewinds B to
`snapshot_at(N - 3)` via Rapier history. Assert:
`validate_and_relay` returns `damageHit = true` iff rewound
position is inside the cone. Assert: rewound position Y matches
Rapier's pre-step capsule centre within 1mm.

### 5.2 The hard questions the codex dispatches will hit

These are the surprises that the codex dispatches WILL hit, called out
now so the briefs can preempt them:

1. **PR 11.7.B: Rapier's `deterministic` feature flag.** The Rapier
   Rust crate has a `deterministic` feature that disables
   non-deterministic optimizations (parallel island updates,
   non-deterministic collision response). For PR 11.7.B, the server
   doesn't need bit-equivalence (see §3.1) — but the **physics
   integration step order** MUST be deterministic across runs (same
   inputs → same state evolution) for damage's `PositionHistory`
   rewinds to be correct. Codex needs to verify the feature flag is
   enabled and that integration tests pass on a fresh `cargo test`
   run.
2. **PR 11.7.B: position history trim cadence.** `PositionHistory`
   retains 64 frames at 64Hz = 1s of history. The existing trim is
   "implicit on next record" (PR 11.6.D §3.4). When the source flips
   from client `PositionUpdate` (sparse, ~32Hz) to physics tick
   (dense, ~64Hz), the trim cadence naturally speeds up — verify
   this doesn't cause retention window drift.
3. **PR 11.7.C: the StrictMode race that bit PR 11.6.D fix4.**
   Predictor + Interpolator are constructed during `createScene`; if
   React's `<StrictMode>` double-mounts `createScene` in dev, the
   predictor gets constructed twice. The pattern from PR 11.6.D's
   fix4 (synchronous IIFE claims the slot before the first `await`)
   applies here too. Brief should explicitly call this out so codex
   doesn't ship a "lazy init" pattern that races.
4. **PR 11.7.C: Vitest test for reconciliation.** The smoke
   `damage-server-hp-convergence-smoke.mjs` already exists and tests
   damage convergence. The new `predictor.test.ts` needs to pin the
   reconciliation invariants: drift > threshold triggers; clamp on
   snap distance; StateAck cadence. Without vitest, only the smoke
   catches regressions — same load-bearing gap PR 11.6.D's `fix5`
   closed.
5. **PR 11.7.D: the 4 lockstep smokes need rewriting, not deletion.**
   The smoke *behaviors* (two-tab handshake, rollback, wire-format
   pitch/yaw) are still valuable; they just need to operate against
   `ServerTransport` (snapshot bytes) instead of `ggrsRuntime` (frame
   bytes). Codex's instinct will be to delete the smokes — the brief
   must call out "rewrite, don't delete."
6. **PR 11.7.E: reload is server-authoritative, not client-side.**
   The instinct will be to do client-side reload (R key → wait 1.5s
   → ammo refills), then add server validation as an afterthought.
   Per `docs/PR-11.6-plan.md` §3.4.2's "trivial-cheat day-one
   defense" rationale, server-authoritative from day one is the
   pattern. Brief: "ship reload as fully server-authoritative; the
   damage-relay validation pattern is the template."
7. **PR 11.7.F: DNS-01 vs HTTP-01 challenge for Let's Encrypt.**
   `rustls-acme` supports both. For Hetzner production, **DNS-01 is
   the right choice** (works across multiple servers + cert rotation
   without HTTP traffic). Codex will probably default to HTTP-01
   (simpler); the brief must call out DNS-01.

### Q1. **Server physics authority: Rapier WASM or Havok port?** — **RECOMMENDED: Rapier WASM (native Rust)**

§3.1 walks through the tradeoffs. The TL;DR: Havok port is 3-4
sessions of work to reimplement capsule + gravity + ground detection
+ jump + wallrun cooldown in Rust, with high risk of latent physics
divergence bugs (PR 11.2.3 wallrun cooldown, PR 11.5 jump condition).
Rapier WASM as a Rust lib (via the `rapier3d` crate) is 1-2 sessions
of integration work with low divergence risk (Rapier is well-known
but its collision response curves differ from Havok's).

**Key insight**: bit-equivalence between client Havok WASM and server
Rapier is NOT required. The server is the source of truth; the client
runs Havok for *predicted local input only*, then reconciles to the
server's Rapier state on snapshot receipt. Drift is bounded by
`RECONCILIATION_THRESHOLD_M = 0.1m`; larger drift triggers a bounded
rubber-band snap.

**My recommendation**: Rapier WASM (native Rust crate).

**2026-08-18 — CALLED: Rapier WASM (native Rust)**. Two player-perceptible
Rapier↔Havok gaps identified (§3.13 coyote-time, §3.14 hitscan-mid-air)

### Q2. **Snapshots at 20Hz (industry floor) or 64Hz (lockstep-equivalent)?**

§3.4 + §3.5 specify `SNAPSHOT_RATE_HZ = 20` (every 3.2 ticks). At
20Hz, the interpolation buffer depth (8 snapshots = 400ms) is more
than enough for smooth remote visuals. Bandwidth math at 24p:
10.7 KB/s/server outbound (down from 21.5 KB/s for per-player
PositionUpdate at 32Hz).

Alternative: 64Hz snapshots (every tick) at 24p = 34.3 KB/s/server
outbound. 3.2x bandwidth cost. Smoothness gain: marginal — the
interpolation buffer depth is the same (8 snapshots = 125ms at
64Hz vs 400ms at 20Hz), but at 64Hz the buffer fills 3.2x faster,
giving the client less time to reconcile drift before the next
snapshot arrives.

**My recommendation**: 20Hz. Industry standard (CS2 = 64Hz with
per-event state pushes, Valorant = 128Hz tick + per-event pushes;
the bare snapshot rate for both is 20-30Hz; per-event pushes carry
the rest).

**2026-08-18 — CALLED: 20Hz**. `SNAPSHOT_RATE_HZ = 20` (every 3.2 ticks)
lands in §3.4 + §3.5. Bandwidth math at 24p: 10.7 KB/s/server outbound.

### 2026-08-18 — 12-HP gap resolution path

PR 11.6.D's 12-HP gap (the optimistic-apply + sweep + recentlySettled
reconciliation workaround) is a load-bearing bug that has cost ~12
hours of debugging time across fix4-fix7 (per `docs/archive/
2026-08-17-fix6-investigation.md`). PR 11.7's snapshot-driven
architecture eliminates the gap as a side-effect:

- Server is the only source of truth for damage timing.
- Client's `applyBroadcast` fires from the snapshot's `damage_log`
  entry (not a separate broadcast).
- Optimistic-apply UX persists (shooter sees HP drop immediately),
  but reconciles against snapshot's `damage_log` on snapshot arrival.
- No sweep, no recentlySettled, no `applyBroadcast` revert path.

**Net effect**: simpler invariant, fewer edge cases, no gap.

This is captured in §4.4 of this plan; the full explanation lives in
the implementation PR (11.7.C), not here.

### 2026-08-18 — Coyote-time + hitscan-mid-air parity (Rapier↔Havok)

PR 11.7.B introduces Rapier as the server physics authority
(Q1, §3.1). Rapier and Havok model ground contact differently
(Havok: support-point persistence ~2 frames past geometric edge;
Rapier: single-manifold contact, 1 frame). Without parity, every
coyote-frame jump produces reconciliation drift (player appears
to fall through jump animation for 1-2 frames) and every mid-air
hitscan rewind through Rapier history has up to 15.6ms position
slop (a target moving at 5 m/s covers ~8cm in that time).

**Decisions**:
- `COYOTE_FRAMES = 2` server-side grant in `physics.rs::apply_jump`,
  matches Havok's empirical 2-frame persistence.
- `WALLRUN_COYOTE_FRAMES = 1` (tighter window per PR 11.2.3).
- `PositionHistory` records every Rapier tick (64Hz) but stores
  every other frame (32Hz storage), `snapshot_at` snaps to nearest
  within ±15ms. Net cost ~30KB/room at 24p.
- Pre-11.7.B Havok-only reference capture (port 5191, Playwright
  2-tab) for ledge walk-off + jump, mid-air hitscan, wallrun
  start. Saved as `client/test-data/{coyote,hitscan-mid-air,
  wallrun-start}-reference.json`. Post-11.7.B smokes (port 5192)
  assert parity within 5cm Y-trajectory and 0 reconciliation
  count on coyote-frame jumps.
- Hit registration edge case (`hitscan_rewinds_through_rapier_history_mid_air`)
  smoke proves the rewind hits the rewound Rapier position
  (not the Havok-predicted position).

**Implications**:
- The "feels like Havok" property (Source-engine coyote-time +
  half-life hit registration) is provable in CI, not just at
  playtest. Two new client smokes (coyote-feel, hitscan-mid-air-feel)
  + three new server integration tests.
- Player-visible regression risk for movement under Rapier-server
  drops to "sub-threshold drift + bounded rubber-band" (the
  existing PR 11.6.D reconciliation model) instead of "every
  ledge jump produces a 1-frame snap."

This is captured in §3.13, §3.14, and §4.5 of this plan.

### 2026-08-18 — PR 11.7.B implementation findings (codex run + verifier review)

PR 11.7.B codex dispatch landed clean on `feat/phase1-pr11.7.b-server-snapshot @ e708d58`
(38m 51s, 27 files, +4597/-110 lines, 2 commits). All 10 verifier gates
green: cargo 168/168, tsc clean, build clean 7,058.04 kB (identical
hash to PR 11.6.D baseline — no server-side type leak), vitest 10/10,
5191 smoke HP=88 baseline PASS, bundle grep clean, Havok reference
capture JSONs exist (coyote + hitscan-mid-air), determinism test
(`snapshot_is_deterministic_across_runs`) PASS.

**Five deviations from the plan-as-written**, each documented in the
relevant commit message + file-level comments + HANDOFF.md. The
verifier (Evo) accepted all 5 as defensible; the plan is amended here
so future reviewers see the canonical resolution rather than the
contradiction:

1. **Rapier 0.12 → 0.18** (Cargo.toml + `server/src/physics.rs`).
   Brief specified 0.12; 0.12 has 112 E0223 ambiguous-associated-type
   errors on Rust 1.95 (Rapier 0.12 predates Rust's lifetime-syntax
   lint promotions). 0.18 is the lowest version that compiles on the
   project's toolchain. Same `dim3` + `enhanced-determinism` feature
   surface (the 0.18 rename of 0.12's `deterministic`). No
   consumer-visible API change.

2. **Rapier 0.18 has no `World` struct** — manual composition of
   `RigidBodySet`, `ColliderSet`, `IslandManager`, `BroadPhase`,
   `NarrowPhase`, `CCDSolver`, `QueryPipeline`, and the
   `PhysicsPipeline` stepper. `PhysicsWorld` newtype in
   `server/src/physics.rs` wraps this so consumer code doesn't depend
   on Rapier's API surface directly. Net cost: ~20 lines of
   struct-field boilerplate per Rapier-version bump mitigation.

3. **`KinematicCharacterController::move_shape().grounded`** for
   grounded detection. Rapier 0.18 dropped `RigidBody::is_grounded()`;
   the canonical API is the character controller (which is what we
   want anyway — official character-grounding primitive). Wrapper
   preserves our internal `PhysicsWorld::grounded(id) -> bool`.

4. **`MoveBits.JUMP = 16` (bit 4), not bit 6** — Brief had a typo.
   Codex read `client/src/net/inputBitmask.ts` correctly. Server
   `physics.rs::apply_jump` now reads bit 4 (= 0x10 = MOVE_JUMP).
   Verified against `inputBitmask.ts` lines 80-89: `JUMP: 16, DIVE: 32,
   SLIDE: 64, WALLRUN: 128`.

5. **`DamageReject` discriminator 0x07 → 0x0C** — Plan-as-written had
   the contradiction mentioned above in the §3.5 callout. PR 11.7.B
   resolved it by bumping DamageReject to 0x0C (outside the
   reserved 0x07-0x0B range). Migration impact: PR 11.6.D clients
   silently warn+drop DamageReject at 0x0C. Damage flow itself
   unchanged; only the rejection notification is lost on legacy
   clients. Documented as a dual breaking change (DamageReject bump
   + the planned `0x06 InputSeq` trailer deferred to 11.7.C).

**All 5 deviations reviewed and accepted by Evo's verifier pass.**
The plan's §3.5 is amended above to reflect the post-implementation
discriminator table; §5 (roll-out) and the Appendix B "carried-forward
decisions" sections need no changes. PR 11.7.B is ready to open.
